## Bug C Fix Details

**Root cause:** `fill_model.refit_loop.refit_once` used `await chain_time.now_cached()` as `window_end_ts` in all modes. In backtest mode, chain time ≈ 2026-05-04 while the replay tick is at 2026-03-xx — fitting on data 25–30 days in the future. CONTEXT.md empirically measured 30× p_fill underestimate.

**Fix diff (refit_loop.py):**
```python
async def refit_once(
    config: BotConfig,
    run_id: str,
    *,
    current_chain_ts: int | None = None,  # NEW
) -> None:
    ...
    if current_chain_ts is None:
        now_s = await chain_time.now_cached()
        window_end_ts = int(now_s)
    else:
        window_end_ts = int(current_chain_ts)  # backtest bound
```

**Regression tests (3/3 GREEN):**
- `test_refit_once_with_current_chain_ts_bounds_window_end`: captures `window_end_ts` arg to `build_features_table`; asserts `<= current_chain_ts`.
- `test_refit_once_without_current_chain_ts_uses_chain_time_now`: mocks `chain_time.now_cached` to `T_LIVE`; asserts `window_end_ts == T_LIVE`.
- `test_refit_once_keyword_only_current_chain_ts`: positional 3rd arg raises `TypeError`.

**Side effect fixed:** removed stale `type: ignore[arg-type]` on `side=side` (mypy strict now accepted it without ignore).

## Loss-Model Decision (Bug C)

**Option A selected: quantify-and-defer.** `loss_model/refit_loop.py` unchanged.

Rationale: loss_model uses 90-day window vs fill_model's 14-day window. With ~25d replay duration, look-ahead fraction = 5d/90d ≈ 5.6% vs 5d/14d ≈ 35.7%. Relative residual bias estimated at <2×. Deferred to post-Plan-04. If Plan 04 verdict lands FLAG, Phase 05.5 investigates loss_model look-ahead as first hypothesis.

Documented in commit `d954bc5` message + wiki page `[[phase-05-4-bug-c-look-ahead-fix]]`.

## Bug D Fix Details

**Root cause:** `_flush_decision_log_to_parquet` wrote `pl.DataFrame(entries)` from a list-of-dicts with heterogeneous keys: HOLD/CANCEL rows lacked `pnl_pendle`, only FILL_REALIZED rows had it. Polars inferred nulls for missing values instead of 0.0.

**Effect:** In-memory aggregation worked (`entry.get("pnl_pendle", 0.0)`). Parquet non-FILL rows had `null` instead of `0.0` — biasing any downstream parquet reader.

**Fix diff (replay.py):**
```python
# Edit 1: per-tick HOLD/CANCEL append (lines ~777-792)
self.output.decision_log.append({
    ...
    "pnl_pendle": 0.0,  # Bug D fix: explicit zero for non-FILL rows
})

# Edit 2: _flush_decision_log_to_parquet write site (lines ~838-839)
df = pl.DataFrame(entries, schema_overrides={"pnl_pendle": pl.Float64})
df.write_parquet(str(part_path))
```

**Regression tests (3/3 GREEN after fix, 1/3 RED on HEAD):**
- `test_pnl_pendle_persists_in_decision_log_parquet`: column exists + dtype `Float64` (PASSES on HEAD due to nullable inference).
- `test_parquet_aggregation_matches_in_memory_to_1e_9_rel`: parquet sum = in-memory sum to 1e-9 rel (PASSES on HEAD).
- `test_non_fill_rows_have_pnl_pendle_zero` (RED on HEAD): non-FILL rows are exactly `0.0` (on HEAD they're `null` → test FAILS).
