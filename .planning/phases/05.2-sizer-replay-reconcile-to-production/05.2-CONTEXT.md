## Why this phase exists

Phase 05.1 produced a binding ship-gate FAIL (run_id `01KQDMC1DC3JW07VG2VMKKXM6T`, then re-run as `01KQDQG0D3TZNZS2QQAPTEAPYJ` after units fix) on BINANCE-ETHUSDT-25SEP2026 long: p5 = 0.0334% USD-APR vs threshold 6.00% USD-APR (delta −5.97 ppt). Operator pushback on whether the strategy could really be 30,000× below the dapp UI's advertised ~1000% APR led to a forensic audit on 2026-04-30 that surfaced **five compounding engine bugs**, not just one. Phase 05.1 was a ship-gate run on a defective engine; the FAIL is therefore not a strategy-viability finding, it's an engine-correctness finding.

Phase 05.2 fixes the engine, re-runs the ship-gate, and produces a verdict that is interpretable in defensible USD-APR units against an engine whose sizing primitive matches the protocol's actual margin model.

## Pendle Boros protocol display change — 2026-04-29 announcement

Display-only change. Protocol math unchanged. Open positions/orders unaffected. Summary:

- **Removed**: Position Value, Leverage
- **Added**: Rate Sensitivity (= 100 × DV01, P&L per ±1% rate move), Daily Volatility (7DMA of implied APR range)

This validates our bug #1 diagnosis: Position Value × Leverage is the wrong frame for rate trading. Our backtest's `q_max` formula encoded the deprecated framing; the team is now publicly aligned with using DV01-style sizing.

**Operational note for Phase 6**: "we will be updating all our API/MCP/SDK to reflect this change as well." Our `@pendle/sdk-boros@1.1.44` will get a breaking update. Pin or upgrade at integration time.

## Open questions deliberately deferred

1. **Effective-pool weighting.** Empirical long pool ~75 YU vs orderbook cumulative ~165 YU. Pendle does some weighting (proximity-to-mid? time-active? something else?). Wave 3 uses parquet sum as proxy. If Wave 5 verdict is materially off prediction, this is the next bug to chase. **E5 (Pendle docs URL) might resolve this without reverse-engineering.**

2. **Cancel race latency.** Phase 6 territory. The ship-gate verdict assumes cancel always succeeds before fill in the simulator. That assumption needs validation in Phase 6 with real Send Txs Bot timings.

3. **Per-market side selection.** For binding market, long-side is 2× more lucrative (smaller pool dominates). Strategy currently doesn't have an algorithmic side-pick. Defer to Phase 6.

4. **Slider position choice.** Min margin (slider=0%) maximizes APR but minimizes liquidation buffer. Trade-off depends on Daily Volatility (E2). Wave 1 implements this as `liquidation_buffer_safety_n` knob; tuning is Wave 5 / Phase 6.
