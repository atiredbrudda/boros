# Phase 05.5 Plan 02: Fill multi-close + loss_model write-side Summary

**One-liner:** Added a per-tick `_pending_close_order_ids: set[str]` guard on
`ReplayEngine` (cleared on tick-boundary advance in `_handle_trade_event`,
consulted by both `_handle_trade_event` and `_detect_inter_event_fills`) so a
single fill produces exactly one `ScheduledClose` instead of N when one
Arbitrum block contains N trade events. Mirrored Phase 05.4-03 commit
`d954bc5` onto `loss_model.refit_loop.refit_once` (now accepts keyword-only
`current_chain_ts: int | None = None`).

## What changed and why

### Bug 2: Fill multi-close

Pre-fix: `ReplayEngine._handle_trade_event` iterates same-block trade events
and schedules a redundant `ScheduledClose` for every event after the first
fill detection (which zeroes `queue_ahead_yu`, making `0 <= evt_size_yu`
True for every subsequent event in the block). Empirical: 11 closes scheduled
for one fill on `initial_01KQTMW2VE7HF408T4V6XV5TDW_long` at ts=1775637304
(PID 18460). Reported fill loss `−1.73 PENDLE`; true cost ≈ `−0.16 PENDLE`
(~11× inflation).

Post-fix: a per-tick guard set `_pending_close_order_ids: set[str]` lives on
`ReplayEngine`. Both `_handle_trade_event` and `_detect_inter_event_fills`
consult the set (skip if order already scheduled this tick) and update the
set (add after scheduling). The set clears in `_handle_trade_event` whenever
`current_ts != _last_handle_trade_chain_ts` — i.e., on tick-boundary advance.

### Bug 1 loss_model write-side mirror

Phase 05.4-03 commit `d954bc5` closed the fill_model write-side; the
loss_model leg was deferred ("If Plan 04 verdict lands FLAG, Phase 05.5
investigates loss_model look-ahead as first hypothesis" — RESEARCH §Open
Question 2 confirmed the mirror is right). This plan mirrored the 14-line

## Clearing site rationale (RESEARCH §Pitfall 5)

The clearing site MUST be `_handle_trade_event` itself, NOT `_maybe_emit_tick`.

The `run()` loop (replay.py:386-402) calls handlers in this order:

  1. `_maybe_anchor_snapshot` (real evt only)
  2. `_maybe_refit_fill_model`
  3. `_maybe_emit_tick`
  4. `_detect_inter_event_fills` (real evt only)
  5. `_handle_trade_event` (real evt only)
  6. `_fire_scheduled_closes`

If clearing happened in `_maybe_emit_tick`, the set would be empty when
`_detect_inter_event_fills` and `_handle_trade_event` later run for each
real event in the same tick — exactly the failure mode the guard exists
to prevent. Clearing at the top of `_handle_trade_event` (when
`current_ts != _last_handle_trade_chain_ts`) is correct because:

  - The set is only mutated by `_handle_trade_event` and
    `_detect_inter_event_fills` (so `_maybe_emit_tick` doesn't need to know
    about it).
  - When `_handle_trade_event` enters with a new `current_ts`, the previous
    tick's bookkeeping is by definition stale (a new tick means new
    same-block scheduling decisions).

## Both call sites covered (RESEARCH §Pitfall 2)

The existing `_detect_inter_event_fills` skip-condition at line 968-970 ("Already
handled by `_handle_trade_event` — skip to avoid double fill") relies on
`queue_ahead_yu == 0` being a stable post-fill flag. The new guard set provides
a second, independent dedup signal that is robust to same-tick same-order
re-checks even when the queue-zero condition would otherwise miss.

Verified by `test_inter_event_respects_guard`: after `_handle_trade_event` has
scheduled a close on event E, calling `_detect_inter_event_fills(E, chain_ts)`
on the same event does NOT add a second `ScheduledClose`.
