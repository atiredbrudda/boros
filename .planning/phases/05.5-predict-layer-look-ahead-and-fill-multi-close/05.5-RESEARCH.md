# Phase 05.5: Predict-Layer Look-Ahead + Fill Multi-Close — Research

**Researched:** 2026-05-06
**Domain:** Boros backtest engine — predict-side artifact retrieval (look-ahead at read layer) + replay multi-close (same-block fill re-firing)
**Confidence:** HIGH (every claim verified against current source/git/disk state in this session)

## Summary

This phase has two coupled bugs that must land together. Bug 1 is load-bearing: every `predict()` and `expected_loss()` call during a historical replay reads a future-dated SQLite artifact (because `get_latest_fit` / `get_latest_loss_grid` have no `current_chain_ts` filter and accumulated rows from prior runs always have larger `window_end_ts` than any historical replay timestamp), then silently coerces `*_age_s = 0.0` and treats the future fit as fresh. Empirical evidence: 266,740 `predict_future_dated_fit` events on a single side in run `01KQYNPPE2CB46414WKHEGCZP5` and zero downstream fill activity. Bug 2 is co-scoped: `replay.py:_handle_trade_event` iterates same-block trade events and schedules a redundant `ScheduledClose` for every event after the queue-drains-to-zero step on the first event — confirmed in code at `replay.py:1490-1500` (no per-tick / per-block guard set).

Both fixes are surgical. The risk is **not** in the fixes themselves; it's in (a) the Phase-4 contract amendment for `*_age_s < 0` (currently silent fresh-coercion; post-fix the branch is unreachable from a correct backtest), (b) plumbing `current_chain_ts` through six caller sites (one production, five operator/breaker/CLI), and (c) re-inserting the multi-close guard without breaking the `_detect_inter_event_fills` skip-condition that already depends on the post-fill `queue_ahead_yu == 0` write.

**Primary recommendation:** Add `current_chain_ts: int | None = None` (keyword-only) to both retrieval functions; default `None` is byte-identical to today (live brain unchanged). At read sites in `predict.py` / `expected_loss.py`, pass `req.current_chain_ts`. Replace the `*_age_s < 0` silent-coercion with a hard `RuntimeError` (Option A) — the chain-ts filter makes negative ages unreachable from a correct backtest, so a `RuntimeError` here surfaces real clock-skew (the original justification for the warn-and-coerce) without paving over the look-ahead path. For Bug 2, add `_pending_close_order_ids: set[str]` to `ReplayEngine`, populate it inside `_handle_trade_event` after scheduling, skip orders already in the set on subsequent events, and clear it at the tick boundary in `_iter_chain_seconds` (or equivalently in `_maybe_emit_tick`). No new BotConfig knobs.

```python
    ...
```

### Pattern 2: Per-tick set guard for same-block re-firing (Bug 2)
**What:** Add `self._pending_close_order_ids: set[str] = set()` to `ReplayEngine.__init__`. Inside `_handle_trade_event`, skip orders whose id is already in the set; after scheduling a close, add the id. Clear the set on the tick boundary.
**When to use:** Any same-block event-multiplicity guard. The set lives at the engine instance because Arbitrum blocks are sub-second (~250ms) and a single 1 Hz tick can cover multiple blocks; bounding the guard at the tick boundary (rather than the block boundary) is the conservative choice — even if 4 blocks fall in a tick, scheduling one close per fill is exactly what we want.
**Example:**
```python
# replay.py:_handle_trade_event
for order in list(self.synthetic_orders.in_flight()):
    if order.order_id in self._pending_close_order_ids:
        continue  # already scheduled this tick — same-block re-fire guard
    if self._trade_consumes_order(order, evt_rate, evt_size_yu):
        sc = self.latency_scheduler.schedule(...)
        self._scheduled_closes.append(sc)
        self.synthetic_orders.update_queue_ahead(order.order_id, 0.0)
        self._pending_close_order_ids.add(order.order_id)
```

```python
# replay.py:_iter_chain_seconds (or _maybe_emit_tick) — clear at tick boundary
self._pending_close_order_ids.clear()
```
[VERIFIED: `_handle_trade_event` lives at `replay.py:1470-1500`; the iteration over `self.synthetic_orders.in_flight()` is the exact site where the guard belongs]

### Anti-Patterns to Avoid

- **Filtering in Python after SELECT:** SQL-layer filter is auditable from query plan; Python-layer filter can be bypassed by future callers. Mirror the LOCKED D-01 discipline (`WHERE data_source = 'operator'` is at the SQL layer for exactly this reason — see `replay.py` docstring line 12-14).
- **Removing the `*_age_s < 0` branch silently:** The branch documents a real edge case (clock rollback). Removing it without supersedence in `[[fill-model-predict-contract]]` and `[[empirical-loss-grid-v05]]` violates Protocol 1.
- **Clearing `_pending_close_order_ids` per-event instead of per-tick:** A single Arbitrum block can have multiple trade events all attributable to one fill. Clearing per-event re-introduces the bug.
- **Forgetting `_get_any_latest_loss_grid` (loss_fit_degraded breaker):** This is a separate copy of the same SQL shape at `breakers/loss_fit_degraded.py:137-156`. Must take the same `current_chain_ts` plumbing or the breaker becomes a back-door look-ahead.
- **Adding a new BotConfig knob:** The fix is fully expressible via existing `current_chain_ts` on `PredictInput` / `ExpectedLossInput`. Adding a knob would require manifest reflection updates (PROTO-04 SSoT — see CLAUDE.md "Engineering Protocols 3").

## Common Pitfalls

### Pitfall 1: Phase-4 contract amendment must include wiki supersedence
**What goes wrong:** Editing `predict.py` / `expected_loss.py` without updating their docstrings and the `[[fill-model-predict-contract]]` / `[[empirical-loss-grid-v05]]` wiki pages would violate Protocol 1 (CLAUDE.md). Both modules carry an explicit `Design-locked. Any change to this signature is a Phase-4 breaking change.` warning at the top of the file.
**Why it happens:** "Just one extra parameter" feels harmless. The pre-commit hook only enforces architecture co-commit (Protocol 2), not wiki co-commit on already-existing wiki pages — Protocol 1 supersedence is a discipline obligation.
**How to avoid:** Plan must include explicit tasks for: (a) update docstring at top of each file from "Design-locked" to "Design-locked v2 — see [[fill-model-predict-look-ahead-read-path]]"; (b) flip `[[fill-model-predict-contract]]` to `Status: Historical — superseded by [[fill-model-predict-look-ahead-read-path]]`; (c) same for `[[empirical-loss-grid-v05]]` and a new `[[loss-model-expected-loss-look-ahead-read-path]]`. Total: 4 wiki pages (2 new + 2 supersede).
**Warning signs:** Plan task descriptions that don't enumerate the wiki page list explicitly.

### Pitfall 2: `_detect_inter_event_fills` already depends on `queue_ahead_yu == 0` being a stable post-fill flag
**What goes wrong:** `_detect_inter_event_fills` at `replay.py:915-1010` includes a `_trade_consumes_order` skip-condition (line 968-970): "Already handled by `_handle_trade_event` — skip to avoid double fill." The Bug 2 fix adds a *second* per-tick guard — but this skip-condition already provides per-event same-tick dedup IF the queue is zeroed. The bug is that `_handle_trade_event` zeroes the queue then re-tests `0 <= evt_size_yu` on subsequent events, which is True. Adding `_pending_close_order_ids` interacts with both handlers.
**Why it happens:** The two handlers were designed to be complementary, not redundant. Neither was designed for same-block multi-event input.
**How to avoid:** The plan must explicitly check `_detect_inter_event_fills` against the new guard. Recommended: have `_detect_inter_event_fills` also check `_pending_close_order_ids` (tracking the bug 2 guard set) so its rate-crossing fallback path doesn't re-fire on the same tick. Test: a single fill with N trade events on the rate-crossing branch must produce exactly 1 `ScheduledClose`, not N.
**Warning signs:** A test that exercises only `_handle_trade_event` and not `_detect_inter_event_fills`.

### Pitfall 3: `loss_fit_degraded` breaker calls `get_latest_loss_grid` AND `_get_any_latest_loss_grid` (a private fallback) — both need `current_chain_ts`
**What goes wrong:** `breakers/loss_fit_degraded.py:92` calls `get_latest_loss_grid(sqlite_path, market_id, side)` for the production path; on test environments with empty `config.markets`, line 97 calls `_get_any_latest_loss_grid(sqlite_path, side)` — a copy of the SQL shape that bypasses market filtering entirely. Plumbing only the public function leaves the private fallback as a back-door look-ahead.
**Why it happens:** Private helpers are easy to miss in grep enumeration if the search is too narrow.
**How to avoid:** The breaker already accepts `current_chain_ts: int` (line 78). Plumb it through both `get_latest_loss_grid` AND `_get_any_latest_loss_grid` (the private helper at `breakers/loss_fit_degraded.py:137-176`). Test: assert that the breaker's two read paths both reject future-dated rows when `current_chain_ts` is supplied.
**Warning signs:** Plan that mentions only `get_latest_loss_grid` (5 read sites listed) and not the breaker's private copy (would make 6 total but only 5 in the table).

### Pitfall 4: CLI / report.py / fill_model.cli call sites have no `current_chain_ts` available
**What goes wrong:** `fill_model/cli.py:142` (operator predict diagnostic) and `fill_model/report.py:40` (operator rollup) read fits with no chain-ts argument. `report.py` iterates all markets and emits a JSON snapshot — there's no per-row chain_ts that would make sense. The right answer is: leave the default (`None`) for these caller — they want the absolute latest, not a chain-ts-bounded view. Same for `fill_model/cli.py:142` (operator diagnostic at wall-clock time per line 154-158: "CLI-only: chain_time not initialised here").
**Why it happens:** Defaulting to `None` preserves these behaviors. The risk is in the production paths (`predict`, `expected_loss`, `loss_fit_degraded` breaker, `replay` indirectly via predict/expected_loss).
**How to avoid:** Plan must enumerate all 5 production read-site calls (`predict.py:80`, `expected_loss.py:90`, `breakers/loss_fit_degraded.py:92` and `:97`, with chain_ts being available at each) and explicitly mark `cli.py` + `report.py` as "operator path — `None` is correct" so the planner doesn't add busywork.
**Warning signs:** A task that adds chain-ts plumbing to operator CLI paths.

### Pitfall 5: `_iter_chain_seconds` is the structural tick boundary, not `_maybe_emit_tick`
**What goes wrong:** Clearing `_pending_close_order_ids` inside `_maybe_emit_tick` would clear it at the 1 Hz decision tick, but `_handle_trade_event` is called *after* `_maybe_emit_tick` in `run()` (line 396 and 401 — the order is `tick → handle_trade → fire_scheduled`). So clearing at tick-emit-time, then handling 11 same-block trade events, would produce 11 closes (the bug is unfixed).
**Why it happens:** Easy to misread the order of calls in `run()`.
**How to avoid:** Clear inside `_iter_chain_seconds` at the boundary BETWEEN ticks (i.e. when chain_ts increments past a 1 Hz boundary). Equivalent: clear it in `_handle_trade_event` itself when the entering `current_ts` differs from a stored `_last_handle_trade_ts`. The plan should specify the exact clearing site and a test that asserts: 11 trade events with the same `blockTimestamp` and the same fillable order produces exactly 1 `ScheduledClose`.
**Warning signs:** A clear-site choice not justified against the call order in `run()` lines 386-402.

```python
def get_latest_fit(
    sqlite_path: Path,
    market_id: str,
    side: str,
    *,
    current_chain_ts: int | None = None,
) -> FitArtifact | None:
    """Return the most-recent-by-fit_window_end_ts artifact for (market_id, side).

    Args:
        current_chain_ts: Optional chain-ts upper bound. None = live mode (unbounded).
            Backtest replay MUST pass the current tick's chain_ts to prevent look-ahead bias.
            See [[fill-model-predict-look-ahead-read-path]].

    base_sql = """SELECT run_id, fit_window_start_ts, fit_window_end_ts, market_id, side,
                         covariate_whitelist, beta, beta_stderr,
                         log_likelihood, deviance, aic, n_observations, converged, fit_status,
                         gof_ks_pval, gof_lr_vs_null, event_index_coverage, created_at
                  FROM fill_model_fits
                  WHERE market_id = ? AND side = ?"""
    params: tuple = (market_id, side)
    if current_chain_ts is not None:
        base_sql += " AND fit_window_end_ts <= ?"
        params = (market_id, side, int(current_chain_ts))
    base_sql += " ORDER BY fit_window_end_ts DESC LIMIT 1"
    with open_connection(sqlite_path) as conn:
        row = conn.execute(base_sql, params).fetchone()
    if row is None:
        return None
    return FitArtifact(...)  # unchanged
```
