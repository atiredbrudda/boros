<decisions>
## Implementation Decisions

### Data source (LOCKED)

- **Authoritative historical source**: `https://historical-data.boros.finance` — public static dump, no auth, no rate-limit observed, "Download folder as ZIP", updated every 2–3 days (last update 2026-04-26 per the site's banner — essentially current).
- **Format**: NDJSON files compressed in ZIP archives.
- **Path layout** (matches Phase-1 ingester 1:1): `market-data/`, `settlement/`, `underlying-apr/`, `market-trades/`, `ohlcv/{5m,1h,1d}/`, `order-book/{market}/raw/`, `order-book/{market}/combined_{tickSize}/`.
- **Per-file URL template**: NOT YET PROBED — researcher must HTTP-probe and document. Likely either (a) directory listing JSON, (b) per-folder presigned ZIP, or (c) static `{kind}/{market}/{YYYY-MM}.ndjson.zip` tree. Don't guess; probe.
- **Underlying-APR exception**: Boros's `underlying-apr/` may already include the funding-rate snapshots needed; if it doesn't, supplement from `https://fapi.binance.com/fapi/v1/fundingRate` for Binance markets, the equivalent OKX endpoint for OKX markets, and HyperLiquid's API for HyperLiquid markets. Decide after probing the Boros archive layout.

### Window + market scope (LOCKED)

- **Trade-tape window**: 60d minimum per DATA-08 screener requirements. Fetch as much as the archive serves up to ~90d if cheap; 60d is the floor.
- **Market candidate set**: the 29 distinct markets currently in `clo_history` (single-snapshot from Phase-1 UAT). Pre-filter on `cloLowerThresh != 0 AND cloUpperThresh != 0` before fetching to avoid burning bandwidth on excluded markets.
- **Ingest concurrency**: parallelizable across markets (each is independent). Sensible cap: 4–8 concurrent fetches to avoid rate-limit surprises on the static host. Researcher to confirm.

### Schema (LOCKED)

- Local SQLite is at alembic head `0002`; Phase 4 added migrations `0003`–`0007`. **Run `cd python && uv run alembic upgrade head` as Wave 0 step 1.** Verify post-upgrade that `market_reward_calibration` (alembic `0006`) exists.
- Pre-commit hooks (architecture_lint, no_plain_keys, etc.) already enforced — no new hook work.

### Reward-budget calibration (LOCKED — Phase 3 D-01)

- Backtest reads `state.market_reward_calibration` rows with `data_source='operator'` (NOT the deprecated `reward_budget_history` table — that's dormant per Phase 3 LOCKED D-01).
- Operator-calibrate via `python -m boros_brain.reward_model calibrate <market>` for each shortlist market AFTER screener+economics-gate produces the shortlist (no point calibrating dropped markets).
- Operator-calibration values come from observable Boros UI / Pendle docs / public statements about per-market `E_liq_per_epoch_pendle`. The CLI is interactive — researcher must document the workflow + expected inputs in a wiki page.

### Fetcher (CLAUDE'S DISCRETION — bounded)

- New file: `scripts/fetch_historical_data.py` — ~50–100 LOC. Or, if better, a Python module under `python/src/boros_brain/data/historical_fetcher/`. Researcher decides the location based on the existing pattern map; preference is for a script (operator-invoked, one-shot) over a module (long-running daemon would conflict with operator-driven nature of the bootstrap).
- **Required behaviors**: download ZIP archives matching `{kind}/{market}/{YYYY-MM}` (or whatever pattern the probe reveals), unzip into a deterministic local layout, log + persist content-length + sha256 per file, idempotent (skip files already present + checksum-matching), structured-log every fetch with `run_id`.
- **Required NOT to do**: live websocket subscriptions (out of scope), retries-with-exponential-backoff for general HTTP 5xx (operator can re-run; keep it dumb), parallelism > 8 concurrent (be polite to the static host).

### Architecture diagram (LOCKED — PROTO-02)

- Add `HistoricalDataFetcher` node to `docs/architecture.yml` with edges to `data/ndjson/` (writes), `state/state.sqlite` (writes via run_manifests), and an external `historical-data.boros.finance` node (depends-on-config).
- Atomic with the fetcher commit. Pre-commit `architecture_lint.py` enforces.

### Wave layout (CLAUDE'S DISCRETION — researcher refines)

Suggested:
- **Wave 0** — schema upgrade + URL-pattern probe + fetcher scaffold (sequential, ~1 plan).
- **Wave 1** — bulk fetch + bulk ingest + AMM conservation validation (parallelizable across markets, ~1–2 plans).
- **Wave 2** — screener + economics gate; **terminal-on-empty-shortlist** (1 plan).
- **Wave 3** — operator reward calibration + fill-model calibration on shortlist (parallelizable across shortlist markets, ~1 plan).
- **Wave 4** — backtest CLI run + ship-gate verdict + perturbation grid + 2D contour + wiki + verdict commit; **terminal-on-FAIL** (1 plan).

Each Wave 2/4 terminal branch must do the engineering-protocols work (kill report, wiki supersedence, STATE.md update) atomically — not as a follow-up.

### What does NOT happen here

- No Phase 6 work (no TypeScript, no `hands` process, no nonce model).
- No multi-market parallel deployment — Phase 5.1 picks the highest-conviction market from the shortlist for the ship-gate run; Phase 6 would deploy that one market.
- No new tests for the engine — Phase 5 covered that. Phase 5.1 adds tests only for the new fetcher and new operator-calibration workflow if the researcher deems them load-bearing.
