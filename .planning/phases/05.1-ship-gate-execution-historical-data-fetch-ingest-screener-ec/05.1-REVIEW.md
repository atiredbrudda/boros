## Summary

Five source files reviewed (plus one empty `scripts/__init__.py`). The fetcher
script (`fetch_historical_data.py`) and replay engine (`replay.py`) are
substantially well-written with strong invariant enforcement, atomic I/O, and
correct security guards. One critical data-corruption bug was found: the shared
`manifest` dict is mutated inside `_record_fetched` from multiple concurrent
threads without any lock, producing a corrupted manifest when `--concurrency > 1`.
Three warnings cover a silent-pass fallback on corrupt zip entries (masking
errors), deferred re-imports of already-imported modules, and a 429 retry that
sleeps on the last attempt before raising — making each rate-limited run take
unnecessarily long. Three info items cover a test using a non-canonical
`decision_kind`, a ZIP-bomb cap that relies on `file_size` metadata (which is
attacker-controllable), and unused archive-kind constants.

## Critical Issues

### CR-01: Race condition — `manifest["fetched"].append()` called from multiple threads without a lock

**File:** `scripts/fetch_historical_data.py:161`

**Issue:** `_record_fetched` mutates `manifest["fetched"]` via `list.append()`.
`_fetch_one_file` calls `_record_fetched` and is submitted to a
`ThreadPoolExecutor` with up to 8 workers (line 974). CPython's GIL does not make
`list.append` + `_is_already_fetched`'s `for entry in manifest["fetched"]:`
iteration pair atomic. Under concurrent reads + writes the following race is
possible:

1. Thread A calls `_is_already_fetched` → iterates `manifest["fetched"]` → sees no
   entry for its URL → proceeds to fetch.
2. Thread B calls `_is_already_fetched` for the same URL concurrently → same result
   → also proceeds to fetch.
3. Both threads fetch, both call `_record_fetched` → two entries for the same URL
   appear in the manifest.

More critically, if Thread A is mid-iteration of `manifest["fetched"]` when Thread
B appends, Python raises `RuntimeError: list changed size during iteration` — an
unhandled exception inside the executor that surfaces only as a logged error and a
partial manifest on disk, leaving the run appearing to have succeeded with `rc=0`
(the errors list is non-empty but the return code check at line 1019–1022 returns
`1` only if `errors` is non-empty after the `as_completed` loop). The manifest
write at line 1008 would still occur, persisting whatever corrupted state was
accumulated.

**Fix:** Introduce a `threading.Lock` guarding all `manifest` mutations and reads:

```python
import threading

# At the top of _run_fetch_loop, after loading manifest:
_manifest_lock = threading.Lock()

# Replace _is_already_fetched and _record_fetched to accept the lock:
def _is_already_fetched(manifest, *, url, local_path, lock):
    with lock:
        if not local_path.exists():
            return False
        for entry in manifest["fetched"]:
            ...  # unchanged logic

def _record_fetched(manifest, *, ..., lock):
    with lock:
        manifest["fetched"].append({...})

# Pass lock= to every _fetch_one_file call in the executor.submit block.
```

Alternatively, accumulate per-thread records as return values from
`_fetch_one_file` and merge them in the `as_completed` loop (single-threaded
merge eliminates the need for a lock entirely).

## Warnings

### WR-01: ZIP-bomb check uses attacker-controlled `file_size` metadata, not actual decompressed size

**File:** `scripts/fetch_historical_data.py:221-225`

**Issue:** `_safe_extract_zip` checks `info.file_size > MAX_DECOMPRESSED_BYTES`
before extraction (line 222). `ZipFile.getinfo().file_size` is the value stored in
the ZIP central directory — it is written by whoever created the ZIP. A crafted
archive can declare `file_size = 0` while containing a 50 GB bomb that only
expands during extraction. The check therefore fails silently for adversarially
crafted archives.

```python
info = zf.getinfo(entry)
if info.file_size > MAX_DECOMPRESSED_BYTES:   # <- attacker controls this field
    raise ValueError(...)
zf.extract(entry, path=out_root)              # <- actual expansion happens here
```

The practical risk is moderate given that the archive source is a known operator
URL (Boros CDN), but if the DNS override (`--resolve`) ever misdirects to a
different host this becomes exploitable.

**Fix:** Stream-extract each entry through a byte counter:

```python
with zf.open(entry) as src:
    total = 0
    with open(dest_path, "wb") as dst:
        for chunk in iter(lambda: src.read(1 << 20), b""):
            total += len(chunk)
            if total > MAX_DECOMPRESSED_BYTES:
                dst.close()
                dest_path.unlink(missing_ok=True)
                raise ValueError(
                    f"zip bomb: entry {entry} exceeds cap {MAX_DECOMPRESSED_BYTES}"
                )
            dst.write(chunk)
```

This measures actual decompressed bytes rather than declared metadata.

### WR-02: 429 handler sleeps on the final attempt before the loop exits with RuntimeError

**File:** `scripts/fetch_historical_data.py:278-289`

**Issue:** When `attempt == attempts` (the last iteration) and the server returns
429, the code executes `time.sleep(wait); continue`. The `continue` does not retry
— the loop terminates and falls through to `raise RuntimeError(...)` at line 312.
The net effect is a mandatory sleep (up to 30 s) with no subsequent retry, whereas
the caller's intent is "if rate-limited on last attempt, surface the failure
immediately." The sleep is wasted time with no benefit:

```python
if resp.status_code == 429:
    wait = backoff[attempt - 1] if attempt <= len(backoff) else 30
    ...
    time.sleep(wait)   # sleeps 30s on attempt==4 (last attempt)
    continue           # loop exits → RuntimeError raised anyway
```

**Fix:** Mirror the 5xx guard pattern — only sleep when a retry remains:

```python
if resp.status_code == 429:
    if attempt <= len(backoff):
        wait = backoff[attempt - 1]
        log.warning(..., wait_s=wait)
        time.sleep(wait)
        continue
    raise RuntimeError(f"Rate-limited after {attempt} attempts: {url}")
```

### WR-03: Silent `return False` on ZIP extraction error discards the exception from the executor

**File:** `scripts/fetch_historical_data.py:562-569`

**Issue:** When `_safe_extract_zip` raises `ValueError` (path traversal or zip
bomb), `_fetch_one_file` catches it, logs an error, and returns `False`:

```python
try:
    extracted = _safe_extract_zip(tmp_zip, out_root=extract_root)
except ValueError as exc2:
    log.error("historical_fetcher.fetch_zip_unsafe", ...)
    return False  # <- counts as "skipped", not "error"
```

From the executor's perspective (`as_completed` loop at line 990) a job that
returned `False` increments `skipped`, not `errors`. A security-relevant event
(path traversal attempt) is therefore reported as a routine skip. The overall
`_run_fetch_loop` returns `0` if the only failures were zip-unsafe entries.

**Fix:** Re-raise a distinct exception (or return a sentinel that the caller maps
to an error entry) so the `as_completed` handler classifies it as an error and the
loop returns non-zero:

```python
except ValueError as exc2:
    log.error("historical_fetcher.fetch_zip_unsafe", url=url, error=str(exc2), **log_kwargs)
    raise RuntimeError(f"Unsafe ZIP rejected: {exc2}") from exc2
```

This ensures the error surfaces in `errors`, the exit code is `1`, and ops is
alerted.

## Info

### IN-01: Deferred re-imports of already-imported top-level modules inside exception handler

**File:** `scripts/fetch_historical_data.py:1122-1123`

**Issue:** Inside the `except Exception` block in `main()`, `json` and `datetime`
are re-imported under aliases (`import json as _json`, `from datetime import UTC as
_UTC, datetime as _datetime`). Both are already imported unconditionally at the
module top-level (lines 45 and 53). This works correctly but is misleading — it
looks like these are first-time imports when they are not, and adds unnecessary
cognitive overhead for readers expecting to find all imports at the top.

**Fix:** Remove the deferred re-imports and use the already-imported names:

```python
except Exception:
    logs_dir.mkdir(parents=True, exist_ok=True)
    date_dir = logs_dir / datetime.now(UTC).strftime("%Y-%m-%d")
    date_dir.mkdir(parents=True, exist_ok=True)
    sidecar = date_dir / f"{manifest.run_id}.manifest.json"
    sidecar.write_text(json.dumps(manifest.model_dump(mode="json"), indent=2))
```

### IN-02: Test uses `"TICK"` as a `decision_kind` value — not in the production schema

**File:** `python/tests/test_backtest_replay_daily_pnl.py:101`

**Issue:** `test_replay_run_bins_realized_fill_pnl_by_day` injects a log entry
with `decision_kind: "TICK"`. The production schema defines only `"CANCEL"`,
`"HOLD"`, and `"PLACE"` as valid values (`decision/schemas.py:55`). The
`_aggregate_daily_pnl` method silently ignores `"TICK"` (it only acts on
`"FILL_REALIZED"` and non-zero `r_share_per_epoch_pendle`), so the test still
passes. However, using a phantom value in a test that exercises production binning
logic reduces test fidelity: if the binning logic is ever extended to cover all
known `decision_kind` values, this test entry will be processed differently than
intended.

**Fix:** Replace `"TICK"` with `"HOLD"` (or another production-valid value). Since
this entry carries no `r_share_per_epoch_pendle` it contributes nothing to either
branch and is effectively a timestamp anchor — `"HOLD"` is the semantically correct
label:

```python
{"current_chain_ts": base_ts, "decision_kind": "HOLD"},
```

### IN-03: `ARCHIVE_KIND_TO_DIR` constant is defined but never referenced in production code

**File:** `scripts/fetch_historical_data.py:80-87`

**Issue:** `ARCHIVE_KIND_TO_DIR` maps archive kind names to output subdirectory
names. The fetch loop (`_run_fetch_loop`) constructs output paths inline (e.g.,
`args.out / "market-trades" / archive_market_id / ...`) rather than using this
mapping. The constant is dead code.

**Fix:** Either wire `_run_fetch_loop` to use `ARCHIVE_KIND_TO_DIR` for output path
construction (which would centralize the kind→dir mapping and catch typos), or
remove the constant if the inline approach is intentional and the mapping is no
longer the design target.
